# Duban 线上 Git 发布流程规范

文档版本：v1.0

适用项目：`duban` 督办事项管理系统

生效范围：代码提交、合并、CI、预发布、生产部署、回滚及发布审计

## 1. 目标与基本原则

本流程要求每一次线上变更都具备唯一版本、明确责任人、可复现构建证据和可执行回滚路径。

1. 生产环境只接受已经合并到受保护 `main` 的代码；禁止直接在服务器修改源码或从个人工作区直接发布未提交改动。
2. 发布顺序固定为：需求确认 → 分支开发 → 代码审查 → CI → 预发布验证 → 审批 → 生产部署 → 线上回归 → 归档。
3. 本地验证是生产发布的前置条件。`check`、`lint`、`build` 只能证明静态/构建质量，不能替代本地 API、浏览器和预发布验证。
4. 代码回滚和数据库回滚分别决策。数据库迁移必须向后兼容，禁止把恢复旧数据库当作默认回滚手段。
5. 所有凭证、数据库连接串、SSH 私钥和环境文件只存在于 CI/服务器密钥存储，不进入 Git、日志或发布记录。

## 2. 分支模型与合并规则

| 分支 | 用途 | 来源/去向 | 保护规则 |
| --- | --- | --- | --- |
| `main` | 生产可发布代码，始终对应当前线上或待发布版本 | 仅接收 `release/*`、`hotfix/*` 的合并 | 禁止直接 push；必须 PR、CI 全绿、2 名审批人（含模块负责人和发布负责人） |
| `develop` | 下一版本集成分支，承载已完成且通过开发自测的功能 | `feature/*`、`bugfix/*` 合入；版本冻结时切 `release/*` | 禁止直接 push；至少 1 名代码所有者审批、CI 全绿 |
| `feature/<issue>-<slug>` | 新功能或较大改动 | 从最新 `develop` 创建，完成后合回 `develop` | 一个需求一个分支；不得混入无关重构 |
| `bugfix/<issue>-<slug>` | 非生产紧急缺陷修复 | 从 `develop` 创建，合回 `develop` | 必须附回归测试或说明为何无法测试 |
| `release/vX.Y.Z` | 发布候选，冻结功能，只允许修复发布阻塞问题 | 从 `develop` 创建；最终同时合回 `main` 和 `develop` | 禁止新增需求；版本号、变更日志、部署说明必须齐全 |
| `hotfix/vX.Y.Z` | 生产 P0/P1 紧急修复 | 从线上 `main` 最新提交创建；最终同时合回 `main` 和 `develop` | 走紧急审批，但不得跳过 CI、预发布冒烟和线上回归 |

合并规则：

- PR 标题使用 `type(scope): summary`，例如 `fix(auth): renew expired token`；正文必须包含需求/缺陷号、影响范围、验证结果、迁移说明和回滚方案。
- PR 分支必须与目标分支同步，解决冲突后重新跑 CI；禁止使用“绕过保护”或强制 push。
- `release/*` 合入 `main` 后立即在同一合并提交上打版本 tag；随后把 `main` 合回 `develop`，避免修复丢失。
- `hotfix/*` 只允许修复生产问题；若包含数据库变更，必须提供向前兼容方案和明确的数据恢复脚本。
- 删除已合并的短期分支；保留 `main`、`develop`、最近两个发布分支的审计记录。

## 3. 版本号与 Tag

采用 SemVer：`vMAJOR.MINOR.PATCH`。

- `MAJOR`：不兼容 API、权限模型或数据契约变更。
- `MINOR`：向后兼容的新功能。
- `PATCH`：向后兼容的缺陷、安全或运维修复。
- 预发布版本使用 `vX.Y.Z-rc.N`，例如 `v2.4.0-rc.1`；不得将 `rc` tag 部署为生产正式版本。

Tag 规则：

1. 只在 `main` 的发布合并提交上创建带注释的签名 tag：`git tag -a v2.4.0 -m "Release v2.4.0"`。
2. Tag 创建者必须是发布负责人，且 PR、CI、预发布验收记录已归档；tag 创建后禁止移动或覆盖。
3. Tag 推送后应触发生产发布候选流水线；流水线必须把 tag、commit SHA、构建产物校验和部署 `releaseId` 写入发布记录。当前仓库尚未配置 `.github/workflows`，在工作流上线前由发布负责人使用受控手工入口执行同等闸门，不得把“手工执行”视为绕过 CI。
4. 线上紧急修复递增 `PATCH`，不得复用旧 tag。撤回版本时记录“回滚到 `vX.Y.Z`”，不删除新 tag。

## 4. 角色、审批与发布窗口

| 角色 | 责任 |
| --- | --- |
| 需求负责人 | 明确范围、验收标准和变更优先级 |
| 开发负责人 | 实现、单测、迁移脚本、回滚方案和发布说明 |
| 模块代码所有者 | 审查业务逻辑、权限、数据范围和兼容性 |
| QA/验收人 | 执行 CI 失败项复核、预发布测试和生产冒烟 |
| 发布负责人 | 检查闸门、批准部署、执行脚本、记录 `releaseId` |
| 值班/运维负责人 | 监控、故障升级、执行回滚和基础设施恢复 |
| 业务负责人 | 对高风险业务变更做最终上线确认 |

常规发布窗口：工作日 10:00–11:30 或 15:00–17:00（北京时间），避开月末、节假日前和批量业务高峰。发布负责人应至少提前 1 个工作日登记变更。生产 P0/P1 可走紧急窗口，但必须在事后 1 个工作日内补齐 PR、审批和复盘。

审批节点：

1. PR 审批：模块代码所有者 + 另一名开发/QA；权限、认证、数据库或部署脚本变更必须增加安全/运维审批。
2. 预发布放行：QA/验收人确认核心流程通过，发布负责人确认版本、依赖、迁移和回滚包齐备。
3. 生产放行：发布负责人和业务负责人双确认；P0/P1 热修复至少由值班负责人替代业务负责人确认风险。
4. 部署完成：发布负责人和 QA 各自完成健康检查及关键业务冒烟，任何一方失败都进入回滚评估。

## 5. 标准流水线

### 5.1 开发与提交

```bash
git fetch origin
git switch -c feature/ISSUE-123-short-name origin/develop
# 修改代码和测试
pnpm run check
pnpm lint
./server/node_modules/.bin/tsx --test <相关测试文件>
git add <本任务文件>
git commit -m "feat(scope): add ..."
git push -u origin HEAD
```

提交必须小而完整，不提交 `dist/`、`server/dist/`、本地 `.env`、数据库备份和临时日志。提交前执行 `git diff --check`，确认没有凭证或敏感数据。

### 5.2 CI 必检项

所有 PR 和 `main`/`release`/`hotfix` push 必须运行（可由 GitHub Actions 或等价 CI 实现）：

1. 依赖锁文件安装（锁定 Node、pnpm、npm 版本）。
2. `pnpm run check`、`pnpm lint`、`pnpm run build`。
3. 前端/后端聚焦测试及全量测试（全量超时必须标红并记录原因，不得静默跳过）。
4. `cd server && npm run build`、`bash -n deploy/deploy-local.sh && bash -n deploy/deploy-server.sh`。
5. 依赖和密钥扫描、迁移/Schema 检查、构建产物归档（绑定 commit SHA 和版本号）。
6. 需要数据库的测试使用隔离临时库，禁止连接生产 `DATABASE_URL`。

CI 失败时禁止合并。仅允许在修复后重新运行；手工点绿、删除失败记录或使用未审查构建产物均视为发布违规。

### 5.3 预发布环境

`release/vX.Y.Z` 创建后自动部署到与生产拓扑接近的预发布环境，使用脱敏数据和独立数据库。QA 至少验证：登录/认证续期、菜单和页面权限、事项创建/审核/签收/反馈、催办/亮灯/消息、导出、附件、移动端关键页面，以及数据库迁移前后兼容性。

预发布验收记录必须包含环境、commit SHA、tag/RC、测试账号类型（不得记录密码）、通过/失败项、截图或 API 响应、已知风险和 QA 签名。任何 P0/P1 失败不得放行。

## 6. 生产发布执行

生产发布前，发布负责人核对：

- `main` 已保护且与目标 tag 的 commit 一致；PR、CI、预发布和审批记录齐全。
- 本地最低验证已通过：涉及 API/数据库时启动 `pnpm dev` 与 `cd server && npm run dev`，调用 `http://localhost:3001/api/health`；涉及 UI 时在 `http://localhost:5173/` 完成真实操作。
- 已生成构建产物、数据库备份、迁移说明和回滚目标 tag；确认当前线上 `releaseId` 和数据库目标。
- 变更窗口、通知对象、监控和回滚负责人已就位。

标准触发方式（默认不自动提交或推送 Git）：

```bash
SSH_KEY=<key-path> bash deploy/deploy-local.sh
```

脚本触发条件：仅允许在审批后的 `main`/正式 tag 工作区执行；工作区不得有未审查改动；构建、后端构建、`rsync`、SSH、PM2/容器重启、数据库结构/内置角色刷新、Nginx 检查必须全部成功。`PUSH_TO_GIT=1` 仅在明确批准时使用，不能作为发布前的隐式提交机制。

现有脚本会生成唯一 `releaseId`，通过公开回环 `/api/health` 验证实际运行时、数据库目标和 runtime 一致后才刷新角色；发布负责人必须把该 `releaseId`、tag、commit SHA、开始/结束时间和脚本日志写入发布记录。完成后至少检查：

```bash
curl -fsS http://49.233.13.110/api/health
curl -fsSI http://49.233.13.110/
```

然后按预发布同一套核心业务冒烟回归。生产 API 健康但业务冒烟失败时，状态记为“部署技术成功、业务发布失败”，不得宣称发布完成。

## 7. 失败处理与回滚

### 7.1 发布中失败

1. 构建/CI 失败：停止发布，修复原分支并重新走 PR；不得从失败流水线取产物。
2. 上传、重启或 `releaseId` 校验失败：保持旧前端/旧运行时可用，暂停数据库角色刷新，检查 `deploy.log`、PM2/容器和 Nginx，再决定重试或回滚。
3. 数据库迁移失败：立即停止后续步骤，保留错误现场；确认迁移是否已部分执行，按迁移专用回退脚本处理，不直接删除生产库。

### 7.2 代码回滚

优先重新部署最近一个已验证的正式 tag（例如 `v2.3.1`），创建 `hotfix` 或回滚 PR 记录原因，再按完整 CI、预发布和审批流程发布。禁止在服务器上手工替换单个 JS/TS 文件。

### 7.3 数据库回滚

只有数据损坏或不可逆迁移才执行数据库回滚。先冻结写入、通知业务和运维、确认备份可读，再使用 `deploy/mysql8-rollback.sh`；该脚本会先导出当前库，但会重建数据库并导入指定 SQL，风险高，必须由运维负责人双人复核参数。数据库回滚后必须恢复兼容的应用版本、执行结构检查、健康检查和业务抽样核对。

### 7.4 回滚判定时限

生产部署后 15 分钟内出现 P0/P1、持续 5 分钟健康检查失败、核心业务无法完成，或错误率/延迟超过变更前基线 2 倍，发布负责人立即召集回滚判断。回滚完成后 10 分钟内完成健康检查和核心冒烟；未恢复则升级值班负责人并进入灾备预案。

## 8. 发布记录与审计模板

每次发布在 `docs/releases/YYYY-MM-DD-vX.Y.Z.md` 或发布系统中记录：

```text
版本/tag：
commit SHA：
发布类型：常规 / hotfix / 回滚
需求与 PR：
发布窗口：
开发负责人 / QA / 发布负责人 / 审批人：
CI 流水线与构建产物：
预发布环境、数据版本与验收结论：
生产开始/结束时间：
releaseId / runtimeId / databaseTargetId：
健康检查与业务冒烟结果：
数据库迁移与备份位置（仅写路径/编号，不写凭证）：
异常、回滚目标、实际结果：
后续行动项与截止日期：
```

发布负责人在发布后 1 个工作日内关闭记录。P0/P1 事件需在 3 个工作日内完成复盘，至少包含时间线、影响范围、检测/响应延迟、根因、为什么闸门未拦截、修复项和流程改进。

## 9. 流程闸门清单

- [ ] 分支、版本号、PR 范围正确，无未审查改动。
- [ ] 代码所有者、QA、发布/业务负责人完成审批。
- [ ] CI 全绿，构建产物可追溯且无密钥。
- [ ] 本地 API/UI 验证通过；预发布核心流程通过。
- [ ] 备份、迁移、回滚 tag 和负责人已确认。
- [ ] 在发布窗口执行 `deploy-local.sh`，记录脚本输出和 `releaseId`。
- [ ] 线上 `/api/health`、前端入口、核心业务冒烟全部通过。
- [ ] 发布记录归档；失败或回滚已通知并创建后续任务。
