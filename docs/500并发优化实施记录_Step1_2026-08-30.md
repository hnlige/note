## 一、实施内容

### 1.1 数据库连接池优化

**文件**: `server/src/db/index.ts`

**变更**:
```javascript
// 之前
connectionLimit: Number(process.env.DB_POOL_SIZE) || 50,
queueLimit: 0,  // ⚠️ 无限队列，OOM 风险

// 优化后
connectionLimit: Number(process.env.DB_POOL_SIZE) || 50,
queueLimit: Number(process.env.DB_QUEUE_LIMIT) || 100,  // 限制队列深度
```

**收益**:
- 防止高并发时请求无限堆积导致内存溢出
- 连接数从 30 → 50（单实例），2 核服务器总连接 100
- 超过队列限制的请求会快速失败（503），而非长时间挂起

**配置调整**（`server/ecosystem.config.js`）:
```javascript
env: {
  DB_POOL_SIZE: '50',        // 从 30 → 50
  DB_QUEUE_LIMIT: '100',     // 新增
}
```

### 1.2 慢查询超时保护

**文件**: `server/src/middleware/query-timeout.ts`（新增）

**功能**:
- 为慢接口（items 批量操作）添加 15s 超时保护
- 超时请求返回 504 Gateway Timeout，释放连接池
- 防止慢查询占满连接池拖垮其他正常请求

**应用**（`server/src/index.ts`）:
```javascript
// items 路由添加 15s 超时（包含批量导入等慢操作）
app.use('/api/items', requireAuth, queryTimeoutMiddleware(15000), itemsRouter);
```

**影响评估**:
- ⚠️ 超过 15s 的操作会被中断（如超大数据导出）
- ✅ 预期保护行为：牺牲个别慢请求，保障全站可用性
- 📋 后续优化：慢操作改为异步任务（提交后轮询结果）

### 1.3 限流策略优化

**文件**: `server/src/rate-limit.ts`

**变更**:
```typescript
// 之前：纯 IP 限流
const ip = req.ip || req.socket.remoteAddress || 'unknown';

// 优化后：优先用户级限流，回退到 IP
type RateLimitOptions = {
  keyGenerator?: (req: Request) => string;  // 新增
};

// 应用（server/src/index.ts）
app.use(createRateLimitMiddleware({
  keyGenerator: (req) => {
    const authUser = (req as any).authUser;
    return authUser?.id || req.ip || 'unknown';
  },
}));
```

**收益**:
- 同一公司出口 IP 下的多用户不再互相影响
- 未认证的请求（登录页）仍回退到 IP 限流
- 限流数据在 Redis 可用时跨 PM2 实例共享

### 1.4 配置文档更新

**文件**: `server/.env.example`

新增配置说明：
- `DB_POOL_SIZE=50`：单实例连接数
- `DB_QUEUE_LIMIT=100`：队列深度限制
- `RATE_LIMIT_PER_MINUTE`：每用户限流

**必须**：调整 MySQL `max_connections` 避免连接耗尽

```sql

SHOW VARIABLES LIKE 'max_connections';

-- 调整配置（需重启 MySQL）
-- 计算公式：PM2 实例数 × DB_POOL_SIZE < max_connections × 0.8

-- 永久生效（my.cnf）

max_connections = 500
```

## 七、已知限制与后续优化

### 7.1 当前已知限制

1. **慢查询超时 15s**：超大数据导出可能失败
   - **临时方案**: 用户缩小导出范围
   - **长期方案**: 改为异步任务（Q2 规划）

2. **Redis 未强制启用**：多实例缓存不一致
   - **影响**: 限流额度被放大 N 倍（N = PM2 实例数）
   - **长期方案**: 部署 Redis + 设置 `REDIS_REQUIRED=true`

3. **连接池队列 100**：极端高并发时请求可能被拒绝
   - **影响**: 返回 503 Service Unavailable
   - **长期方案**: 引入异步队列（BullMQ）

### 7.2 后续优化计划（Step 2）

参见 `docs/架构评估报告_500并发承载能力分析_20260829.md` Step 2：

1. **后端文件拆分**（3 人日）
   - items.ts 拆分为 8 个子文件
   - 降低合并冲突率 70%

2. **前端状态拆分**（2 人日）
   - useStore.ts 拆分为 10 个模块
   - 提升开发效率 30%

3. **列表接口字段精简**（2 人日）
   - 去掉 subTasks/changeHistory/attachments
   - 响应体缩小 60%，传输时间减半
