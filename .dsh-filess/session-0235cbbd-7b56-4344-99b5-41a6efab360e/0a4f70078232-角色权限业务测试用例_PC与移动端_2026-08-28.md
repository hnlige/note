## 一、代码中角色相关条件分支与权限控制逻辑（识别摘要）

### 1.1 三层权限体系 + 服务端模块层

| 层次 | 前端实现 | 服务端实现 |
| --- | --- | --- |
| 菜单/路由层 | `canAccessByAuthCodes`（`src/store/role-access.ts:77-84`，authCodes 含 `ALL` 直接通过）；侧边栏只按 authCode 过滤（`src/components/Layout/Sidebar.tsx:100-106`，菜单项 `roles` 字段**未参与过滤**）；`ProtectedRoute`（`src/components/Common/ProtectedRoute.tsx:27-31`）判定顺序：未登录→跳 `/login`（:39-41）→ `allowedRoles` 不含当前角色→无权提示页（:48-68）→ authCode → extraCheck | `requireModuleAccess(predicate, 中文消息)`（`server/src/routes/module-authz.middleware.ts:8-23`，未授权 403 `{error}`）；`hasAnyPermission` 中 `ALL` 旁路（`server/src/routes/module-authz.ts:34-37`） |

| 行级数据层 | `filterVisibleItems`（`src/store/item-access.ts:197-251`）：共享→跟进人直属上级→owner 维度 scope→follower 维度兜底；`getEffectiveRoleScope` 多角色取最大权重（:40-58） | `getValidRoleForUser` 多角色合并（`server/src/routes/access.policy.ts:321-363`，scope 取权重最大 SELF:1<…<ALL:5，orgIds/自定义人员取并集）；`getOwnerScopeSubjectIds`/`getFollowerScopeSubjectIds`（:170-235）；SQL 下推 `buildItemAccessWhere`（:477-539，无角色→`0=1`）+ 内存复核 `filterItemsByAccess`（:371-418）双层 |

### 1.2 角色→身份映射与关键旁路分支

- 前端 `UserRole` 仅三值（`src/types/index.ts:1`）：`mapRoleIdentityToUserRole`（`role-access.ts:62-71`）——roleIds 含 `r1/r4dtsn6m`→ADMIN；含 `r2`→FOLLOWER；**其余（含 r3、r6、r5）→OWNER**。
- 服务端 `getUserRoleKind`（`server/src/lib/item-scope.ts:288-298`）：roleIds 含 `r1/r4dtsn6m` 或旧角色名（超级管理员/系统管理员/督办管理员）→`'ADMIN'`。
- `hasGlobalPrivilege`（`items.ts:603`：`role==='ADMIN' || permissions 含 'ALL'`）豁免多数行级身份校验，**但对 APPROVE_ITEM 不豁免**（`items.ts:677-683` 仍要求跟进人或跟进人直属上级）。
- `ensureItemActorAllowed`（`items.ts:615-693`）核心分支：
  - `SIGN_ITEM/FEEDBACK_ITEM/DELAY_ITEM`：非责任人→403「仅事项责任人可执行该操作」；签收无计划日期→400「签收前请填写计划完成日期」；反馈时本人子任务 PENDING→400「请先签收并填写计划完成日期后再反馈」、OVERDUE→400「子任务已超时，请先申请延期后再反馈」。
  - `URGE/CHANGE/SUSPEND/RESTART/DISABLE/REJECT/MARK_UNSATISFIED/DELETE_ITEM`：非跟进人→403「仅事项跟进人可执行该操作」。
  - `APPROVE_ITEM`：非跟进人且非跟进人直属上级→403；无上级时兜底 ADMIN/ALL 用户为终审（`getFollowerSupervisorIds`，`items.ts:402-428`）。
  - `APPLY_COMPLETE_ITEM/SHARE_ITEM`：非相关人员→403。
- 回收站归属：非管理员仅能操作 `deletedById===自己` 的事项（`items.ts:1470-1475、2261-2266`）。
- `isDeptManagerLike`（`access.policy.ts:151-158`）：r3 或 DEPT scope → 仅扩大数据范围（本部门+子部门+汇报链下属+自定义人员，:136-145），**不授予任何写操作**。

### 1.3 服务端不信任客户端字段的原则（越权用例设计依据）

- 时间线节点身份/时间由服务端重建，客户端提交的 APPROVE/REJECT/STATUS 类节点被丢弃（`items.ts:165-211`）。
- 软删除元数据 `deletedAt/deletedById/originalStatus` 服务端生成（`items.ts:1490-1508`）；恢复只能回 `originalStatus`。
- 签收计划日期 `getPlannedCompletionDateForSign` 服务端覆盖（要求完成日期优先，责任人不可自定义覆盖，`items.ts:1456-1463`）。
- 催办 sender 取服务端身份、接收人必须属于该事项（`urge.ts:250-273`）；幂等键唯一索引去重（`urge.ts:299-303`）。
- 消息已读/删除仅限本人可见消息（`messages.ts:97-102、143-147`）。
- 角色鉴权全用 DB roles 行，请求体 `role` 仅作显示名兜底（`users.ts:67、243`）；不能给自己授予 r1/r4dtsn6m（`users.ts:226`）。
- 企业微信登录只信 code 换取的 UserID（`server/src/routes/wecom.ts:30-90`），`/wecom/config` 公开但不含 Secret。
- TEXT 列 JSON 规整+身份回填必须在权限过滤前执行（历史 403 误判回归点）：列表 `items.ts:732`、详情 `:821`、更新 `:1363-1366`、催办 `urge.ts:245/369/547`、附件 `attachments.ts:56-59`。

### 1.4 已识别口径疑点（用例中标记 ⚠，需产品/开发确认，非确认缺陷）

1. **r3 部门管理员：侧边栏可见「统一台账/催办管理」，但路由被拒**。侧边栏只按 authCode 过滤（`Sidebar.tsx:102`），r3 permissions 含 `MENU_STATISTICS/MENU_MONITORING`（`built-in-roles.ts:34`）；而路由 `/statistics`、`/monitoring` 的 `allowedRoles=['ADMIN','FOLLOWER']` 且优先校验（`App.tsx:62,64` + `ProtectedRoute.tsx:27-28`），r3 映射 OWNER → 点菜单进「无访问权限」页。→ 用例 DE-05。
2. Items 列表预览抽屉「催办反馈」按钮误用 `canDeleteItems` 判定（`src/pages/Items/index.tsx:630-637`），按钮显隐口径与业务动作不符。→ 用例 SEC-11 附带观察点。
3. 按钮判定双口径并存：页面级 `canUsePageAction`（空=无授权）与全局 `canUseAllowedAction`（空=全允许）语义相反（`role-access.ts:94 vs :118`），不同页面取用不同。→ 用例 SEC-11。
4. 移动端「我的-退出登录」只清 token 不清 `duban-storage`（`src/pages/Mobile/Mine.tsx:60-68`；store 的 `logoutUser` 清双 key，`useStore.ts:646-647`），存在身份残留风险。→ 用例 XP-12。
5. 移动端首页「高频待办」排序用简化天数（不含当天+1，`Home.tsx:80-82`），与展示用 `remaining-days.ts` 口径不同（仅影响排序，低风险）。

## 十三、执行建议

1. **优先级**：SEC 越权组（角色隔离红线）＞ 各角色正常核心流（SA/FO/OW）＞ XP 交叉 ＞ EN 引擎（需等待周期，放最后）；第十一节补充用例中 **P0 与 ⚠ 缺陷候选（SUP-11/16/28）与 SEC 组同批优先执行**，P1 随对应角色组，P2 视排期。
2. **环境**：全套建议在本地/测试环境执行（`pnpm dev` + `cd server && npm run dev`）；涉及 UI 走 `http://localhost:5173/`，API 用 `curl http://localhost:3001/`。**线上仅抽样只读用例+`/api/health`**，写操作（转交/停用/角色变更/永久删除）严禁在线上执行。
3. **API 级越权用例**（SEC 组）用 curl/脚本携带各角色 token 直调，勿只依赖 UI 按钮隐藏判断。
4. 引擎类用例（EN/XP-03）需预留 ≥2 个引擎周期（默认 120s）观察窗口。
5. 结果记录区分证据层级：源码推断 / 本地 API / 本地浏览器 / 线上验证；⚠ 标记的疑点用例（DE-05、SEC-11、XP-12、SUP-11/16/28）结论需同步产品/开发确认预期——其中 SUP-11/16/28 为「代码推断与安全预期不符」的缺陷候选，复现后先提缺陷单，不改用例预期。
6. **teardown/数据复位**：写操作用例执行后必须恢复——新建事项删除清理；SA-07/SUP-12 转交与改人后改回原责任人/跟进人；SA-10/SUP-07 停用与角色清空后恢复账号角色；SUP-06 角色配置改回基线（注意内置角色授权字段以 `built-in-roles.ts` 为准）；SUP-21 引擎参数复原；SUP-28 部门环解除。建议维护初始化 SQL/脚本保证可重复执行。
7. **环境差异**：开发环境 401 不跳转登录页（`api.ts:81-92` 仅生产生效）——XP-07 的跳转断言仅生产成立；访问上下文缓存 TTL 开发 2s/生产 60s（`access.context.ts:5-6`）——影响 SUP-06、DE-07 等角色/范围变更类用例的等待时间。
8. **断言口径**：403/400 中文文案为次级断言，主断言用 HTTP 状态码+业务结果（状态值、可见性、计次），避免后端文案微调造成误报。
9. **自动化挂接**：SEC 组与 SUP-01/02/06/07/16/23 天然适合 API 脚本化（curl/脚本携带各角色 token 直调）；UI 侧可并入既有 `pnpm test:e2e`（Playwright）冒烟层；本集定位为「人工全量 + 自动化抽样」双层使用。
